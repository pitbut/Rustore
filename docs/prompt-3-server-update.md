## 1. Капитан выбирает, кто отвечает (главное правило игры)

Новая фаза **`CHOOSE_ANSWERER`** между `DISCUSS` и `ANSWER`:

```
… DISCUSS → CHOOSE_ANSWERER (10 с) → ANSWER (30 с) → CHECK → REVEAL → SCORE …
```

- После обсуждения (или досрочного «Ответ готов» капитана) сервер шлёт `game:phase {phase:"CHOOSE_ANSWERER", endsAt: now+10000, round, sector}` и `host:say {text:"Капитан, кто будет отвечать?", voiceStyle:"host"}`.
- Капитан шлёт **`game:choose_answerer {playerId}`** — любой участник команды (в том числе он сам). Проверки: отправитель — капитан (иначе `error {code:"not_captain"}`), фаза `CHOOSE_ANSWERER` (иначе `wrong_phase`), `playerId` — участник команды этой комнаты (иначе `not_member`). Выбор принимается один раз, фаза сразу заканчивается.
- **Капитан не выбрал за 10 с — отвечает сам капитан.**
- Капитан-бот выбирает сам (через 1,5–4,5 с, случайного участника; иногда не успевает — тогда отвечает он).
- Сервер шлёт новое событие **`game:answerer {playerId, seq}`** и записывает `answererId` в `RoomState` (новое поле, сбрасывается в `null` на `SPIN`, на новом `game:question` и на `DISCUSS`).
- Затем `ANSWER` длится **30 с** (`endsAt: now+30000`). `game:answer` принимается **только от `answererId`** (иначе `not_answerer`). Бот-отвечающий отвечает через 2,5–6,5 с. Нет ответа до конца — пустой ответ (очко зрителям).
- **Суперблиц:** фаза `CHOOSE_ANSWERER` пропускается, `answererId = superblitzPlayerId`, событие `game:answerer` всё равно отправляется.
- **Блиц:** выбор делается перед каждым из трёх вопросов (как в моке).
- «Ответ готов» (`game:ready_answer`) по-прежнему жмёт капитан (в суперблице — выбранный игрок), копилка времени не меняется.
- Переподключение: `room:state` содержит `phase` (`CHOOSE_ANSWERER` с `endsAt`) и `answererId`.
- Если `answererId` отключился во время `ANSWER` — ждать до конца 30 с (его место держится 90 с), ответа нет → очко зрителям.
- Обнови движок, типы фаз (enum `Phase`), валидацию Zod, документацию контракта и тесты:
  - капитан выбрал игрока → отвечает он, `game:answer` от других → `not_answerer`;
  - капитан не выбрал → `answererId` = капитан;
  - выбор не-капитаном → `not_captain`; выбор чужого игрока → `not_member`;
  - суперблиц без фазы выбора;
  - полный цикл игры до 6 очков в интеграционном тесте проходит с новой фазой.

## 2. Вход через Google

Новый эндпоинт **`POST /api/v1/auth/google {idToken}`** → тот же ответ, что у `/auth/login`: `{accessToken, refreshToken, expiresAt}`.

- Проверка ID-токена Google библиотекой `google-auth-library` (`OAuth2Client.verifyIdToken`), `audience` = значения из `.env` **`GOOGLE_WEB_CLIENT_IDS`** (через запятую). Проверить `iss` (`accounts.google.com` / `https://accounts.google.com`), срок, `email_verified === true`.
- Если пользователь с таким `googleSub` есть — войти. Если нет, но есть аккаунт с тем же e-mail — привязать `googleSub` к нему и войти. Иначе создать аккаунт: `email` из токена, `emailVerified = true`, пароль не задан (вход по паролю для него невозможен, пока не сделают «забыл пароль»), ник — из `given_name`/`name`, обрезать до 24 символов, при занятости добавить цифры (`Аня`, `Аня2`, …), аватар — случайный 0–11.
- Миграция Prisma: поле `googleSub String? @unique`, `passwordHash` сделать необязательным.
- Ошибки: неверный/просроченный токен → `401 {"error":{"code":"invalid_token"}}`; e-mail не подтверждён в Google → `400 {"error":{"code":"google_email_unverified"}}`; `GOOGLE_WEB_CLIENT_IDS` пуст → `503 {"error":{"code":"google_disabled"}}`.
- Rate-limit как у `/auth/login`. В лог — только `sub` хешем, без e-mail.
- `GET /api/v1/config` → `features.googleSignIn: true`, если ключ задан.
- `DELETE /me` удаляет и привязку Google.
- Тесты с замоканным верификатором (новый пользователь, существующий по e-mail, повторный вход, неверный токен).

Что нужно от меня (спроси, если не задано): значение `GOOGLE_WEB_CLIENT_IDS` — Web client ID из Google Cloud Console.

## 3. Надёжное продление сессии (чтобы не выкидывало из аккаунта)

Сейчас повторное использование старого refresh-токена отзывает всю сессию. Клиент теперь продлевает строго по одному запросу, но мобильная сеть может потерять ответ (запрос дошёл, ответ — нет), и тогда клиент повторит тот же refresh-токен.

- Добавь **окно благодати 60 с**: если старый refresh-токен предъявлен повторно в течение 60 с после ротации **с того же устройства/сессии** — вернуть ту же новую пару токенов (сохранённую при ротации), а не отзывать сессию. После 60 с — как сейчас (отзыв = защита от кражи).
- Refresh-токен — 60 дней с продлением при каждом использовании (скользящий срок), чтобы активный игрок никогда не вводил пароль заново. Access — 15 мин без изменений.
- Socket.IO: при истёкшем access-токене в рукопожатии отвечать `connect_error` с сообщением **`unauthorized`** (клиент по нему продлевает токен и переподключается).
- Тесты: двойной refresh в течение 60 с → одинаковая пара; через 61 с → 401 `invalid_token`; рукопожатие с истёкшим токеном → `connect_error` `unauthorized`.
